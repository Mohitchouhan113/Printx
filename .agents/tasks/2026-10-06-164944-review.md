# Dynamic subscription plans — iteration 2 review

This change introduces a server-side printer-add API route, fixes an analytics data-fetch race against the plan gate, removes a dead `PLANS` import from the upload route, and documents a deliberate null-expiry admin backdoor in `getShopActivePlan`. The core subscription expiry-extension logic, the dynamic billing UI, and the order quota enforcement from the previous iteration are all confirmed intact.

**Watch for:**
- **confirmed** — The printers page (`/vendor/dashboard/printers`) bypasses the new `/api/printers/add` route entirely. New printers are still inserted directly from the browser via the Supabase client. The server-side quota guard returns 403 to nobody.
- **confirmed** — `fetchPlans` in `plansStore.js` never selects `has_analytics`; the analytics page's DB path for the gate always receives `undefined` and silently falls through to the static `lib/plans.js` fallback. The dynamic DB-driven analytics gate is a dead code path.
- **confirmed** — The billing plan cards are still enumerated by the hardcoded `PLAN_ORDER = ['free','basic','pro','advance','lifetime']` array, not by the rows returned from the DB. If the admin creates a new plan in Supabase it will never appear on the billing page.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The server-side printer quota in `/api/printers/add` returns 403 correctly, but the printers page `handleSave` inserts directly into Supabase via the browser client for new printers — it never calls the route. The route exists and compiles, but enforces nothing in the real flow. UI-level enforcement (`openAdd` shows a toast) is client-side and bypassable.

The analytics feature gate was fixed to call `fetchJobs` only when `hasAnalytics !== false`, which closes the data-fetch race. However the DB lookup for `has_analytics` can never succeed: `fetchPlans` in `plansStore.js` explicitly selects a fixed column list that omits `has_analytics`. The gate always resolves via the static fallback in `lib/plans.js`, which works correctly for the current plan set but will not reflect admin changes to the flag in Supabase.

`getShopActivePlan` handles expiry, lifetime, and the null-expiry backdoor correctly. The `computeExpiryFromBase` function in `subscriptionService.js` extends from the current active expiry when it is genuinely in the future, and falls back to `Date.now()` otherwise — the upgrade preservation bug is fixed. Progressive column-drop is applied throughout shops, subscriptions, and wallet_transactions writes.

The billing UI's plan-card loop iterates over the hardcoded `PLAN_ORDER` constant. Dynamic DB rows from `fetchPlans` are used only to override price, offer badge, and features on those five static slots. Any plan the admin adds to the DB that does not have a matching entry in `PLAN_ORDER` will not render.

The build verification file is present and records a clean pass with all four changed routes confirmed in the output. The verify file is credible.

### Printer quota enforcement: server route exists, UI bypasses it

`/api/printers/add` fetches the active plan via `getShopActivePlan`, counts the shop's existing printers with a server-side Supabase query, and returns 403 + `planLimitReached: true` when the count meets or exceeds `max_printers`. This is confirmed correct server-side code.

The printers page `openAdd` checks `maxPrinters !== -1 && printers.length >= maxPrinters` before opening the modal — UI-only, client-bypassed. When the user gets past that check and submits the form, `handleSave` for new printers (the `else` branch, line ~252) calls:

```js
const { error: insertErr } = await supabase
  .from('printers')
  .insert([insertPayload])
  .select();
```

This is a direct Supabase client write. The `/api/printers/add` route is never called. Because the Supabase anon key has insert rights on the `printers` table (required for other operations), this insert succeeds regardless of plan limits.

### `has_analytics` DB gate is dead code

The analytics page reads the feature flag in a `useEffect` that calls `fetchPlans()`, filters active rows, finds the matching plan by `code`, then checks `planRow.has_analytics`. `fetchPlans` in `plansStore.js` builds its query with:

```
'id, code, name, original_price, offer_price, billing_cycle, badge_tag, features, is_active, created_at'
```

`has_analytics` is not in this list. PostgREST will not include the column in the response even if it exists in the table. `planRow.has_analytics` is always `undefined`, the `!== undefined` check fails, and execution falls through to the static PLANS catalog. The static catalog has correct values for the current five plans, so the gate still works — but it cannot be controlled from the DB, which is the stated goal of this feature.

The same missing-column gap affects `has_whatsapp_bot`, `has_custom_poster`, `max_printers`, and `max_orders_monthly` in any client-side plan fetch (printers page, analytics page, VendorShell sidebar). Server-side routes that go through `getShopActivePlan` are unaffected because that function selects those columns directly from the `plans` table with a separate query.

### Billing UI: PLAN_ORDER still controls card rendering

`BillingContent` maps over:

```js
const PLAN_ORDER = ['free', 'basic', 'pro', 'advance', 'lifetime'];
{PLAN_ORDER.map((planId, i) => { const plan = PLANS[planId]; ...
```

`dynamicPlans` from the DB is used to build `resolvedPlans`, a lookup map that overrides price, `offer_price`, `badge_tag`, and `features` for matching plan IDs. But the card grid will always have exactly five slots keyed to those five string IDs. A plan with `code = 'enterprise'` added in Supabase has no slot in `PLAN_ORDER` and no fallback in `PLANS`, so it never renders.
